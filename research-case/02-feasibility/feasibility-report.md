## 10. Pilot or evidence-acquisition plan

- Decision-relevant uncertainty: can the benchmark core be instantiated from public evidence with rerunnable admissibility manifests, independence assignments, exploit-status rules, and one frozen baseline before any definitive study design
- Why a pilot is needed, or why a safer evidence step is sufficient: the unresolved items are design- and execution-critical but reversible; a bounded pilot is safer than corpus-scale assembly and does not require live targets, nonpublic data, or partner operations
- Smallest safe informative test:
  - assemble a small public-only pilot cohort with enough heterogeneity to test multiple protocol lineages, clone relationships, proxy patterns, and exploit mechanisms
  - generate case-level admissibility manifests and provenance bundles
  - independently rerun lineage/clone/mechanism assignments on the same pilot cases
  - trial a mature-negative/unresolved status rubric on public follow-up examples
  - reproduce one frozen baseline or formally justify a substitute public baseline
- Measure and denominator:
  - manifest completeness: pilot cases with all critical fields completed lawfully / all pilot cases
  - rerun agreement: pilot cases whose split eligibility is unchanged under independent rerun / all rerun cases
  - status-rule operability: public follow-up cases that can be assigned confirmed-positive, mature-negative, or unresolved without ad hoc exceptions / all status-trial cases
  - baseline reproducibility: planned baseline steps reproduced in a clean environment / planned steps
- Sample/run/precision rationale: information sufficiency rather than efficacy power; the pilot must contain enough diversity to expose at least one disputed case type in lineage, clone, mechanism, and status assignment, plus enough benchmark plumbing to test baseline reproduction
- Maximum cost, time, exposure, and data sensitivity:
  - cost: bounded local compute and publicly accessible artifacts only
  - time: short, reversible pilot before any definitive study design
  - exposure: no live-target interaction, no disclosure outreach, no proprietary data
  - data sensitivity: public-source records only
- Green/amber/red thresholds:
  - green: all critical pilot criteria in `progression-criteria.csv` pass at green level
  - amber: core pilot is technically possible but needs ontology/rule refinement before study design
  - red: any fatal pilot criterion shows that the benchmark core cannot be executed lawfully or reproducibly under current scope
- Stopping conditions:
  - any pilot case requires nonpublic or post-cutoff evidence for a critical manifest field
  - independent rerun changes split eligibility in a way that cannot be resolved by prespecified rules
  - no public-data baseline can be reproduced or justified
  - any source-rights blocker prevents lawful pilot continuation
- Interpretation for proceed, modify, repeat, redesign, or stop:
  - proceed: benchmark core may request `GO TO STUDY_DESIGN`
  - modify/repeat: refine ontology, status rules, or tooling and rerun only the affected pilot slice
  - redesign: narrow contribution to a simpler retrospective benchmark without the failed surface
  - stop: abandon the full ChronosAudit interaction claim if a fatal core assumption fails
- Pilot-to-definitive data relationship, contamination risk, and reuse rule: pilot artifacts are for feasibility only; any pilot cases later reused in definitive analysis must be disclosed explicitly, and confirmatory performance claims must use separately frozen rules and a contamination-aware split policy
